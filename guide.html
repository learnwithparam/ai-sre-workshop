AI SRE facilitator guide

You run a real incident in front of the room. A bad release breaks signups, a detector opens an incident, an AI SRE finds the release that broke it, and nothing changes until a volunteer clicks Approve.

Every module asks the room to answer a question with SQL first. Then it shows the same answer in the ClickStack UI. Then it hands that answer to the agent as a tool. Module 5 is the same loop the lab's end-to-end suite drives with a real model and a real browser.

09:30 to 11:00 · Module 1

The data an agent reasons over

Goal

Attendees can read the schema and get p95 latency per endpoint, from every span, in one query.

Say

Problem: an agent can only reason over what was stored, so start with the storage. Traces are rows in otel_traces, sorted by service, span name and time. A query for one service reads a small slice, not the whole table.

New facts arrive all the time. Attributes live in Map columns, so a new fact needs no migration. Point at the compression ratio in list_tables: keeping data costs money before any model is involved.

One trap to show on screen. The Go service writes its trace id into LogAttributes['trace_id'], not the TraceId column. Agents fall into this, and ours did.

Run

docker exec -it clickstack clickhouse-client --param_minutes=30 --param_service=subscription-backend

Paste these three blocks from the file below, one at a time, and read the comment above each one aloud before you run it.

list_tables          -- what ClickStack keeps, how much of it, and how well it compresses
list_services        -- who reports telemetry, with releases and error counts
latency_percentiles  -- p50, p95, p99 and error rate per endpoint, over every span

11:00 to 12:30 · Module 2

Anomaly detection inside the database

Goal

Attendees can write a three sigma bound in SQL and name the two guards a real detector adds.

Say

Problem: how does the system know a minute is bad? Compare the last minute with a band: the baseline mean plus three standard deviations.

On a silent baseline the band is zero, so one failed request would page. The floor fixes it: min_delta of 5 points.

Two problems remain. A past outage stretches the band and hides the next one, so the detector drops those buckets. And with no clean baseline yet, it uses a fixed 10% ceiling. Show both in the detector file, then the unit test that pins them.

Last, a dashboard should not scan every span. The materialized view keeps per-minute rates ready on every insert.

Run

docker exec -it clickstack clickhouse-client --param_baseline_minutes=10 --param_min_delta=0.05 --param_service=subscription-backend --param_minutes=60
service_timeseries          -- requests, errors, error rate and p95 per bucket
analyze_service_anomalies   -- the 3 sigma bound, per service, with a floor
error_rate_window           -- the buckets the detector reads, timestamps kept
service_minute_rates        -- the same rates, read back from the materialized view

13:30 to 15:00 · Module 3

Finding what changed

Goal

Attendees find a real fault by hand, with event deltas and a trace waterfall, before any agent touches it.

Say

Problem: the detector says something is wrong, and it cannot say what. Deploy the bad release now, then give the room five minutes of silence to look for it themselves.

Step one: compare the last five minutes with the five before. New patterns float up and steady noise cancels out. Step two: break errors down by service.version. Step three: open one failing trace.

Attendees repeat this at work on Monday, so hand them the keyboard. Every step is a query they can run on their own ClickHouse tonight. Reset at the end. The hour before Module 5 gives the detector a clean baseline.

Run

make chaos SCENARIO=bad-release
docker exec -it clickstack clickhouse-client --param_service=subscription-backend --param_incident_minutes=5 --param_minutes=15
get_event_deltas      -- log patterns that are new or growing, ranked
error_span_deltas     -- the same delta over spans, by endpoint and release
errors_by_release     -- the failure broken down by service.version
event_patterns        -- a window of logs clustered, with one example each
sample_error_traces   -- failing traces first, then the slowest: the evidence
get_trace_waterfall   -- one trace, span by span, with its SQL
trace_logs            -- the log lines that belong to that trace

Take a trace id out of sample_error_traces and pass it as --param_trace_id. When the room has the answer:

make chaos-reset

15:00 to 16:15 · Module 4

Tools an agent can be trusted with

Goal

Attendees can say why the lab gives the model ready-made tools, a read-only SQL escape hatch, and exactly one tool that can act.

Say

Problem: raw text-to-SQL fails in predictable ways. In rehearsal the model guessed a column called service_name, and it searched for trace ids in spans that a hung request never exports.

So the lab gives the agent ready-made tools. Open the table below on screen. Every tool is one of the queries the room wrote this morning, with the arguments filled in and the results trimmed. The agent does no analysis the room has not done by hand.

Two stories from building it. A bare release argument on propose_remediation made the model fill in the release to roll back to. And a "no spans" answer for a hung request sent the model into a dozen raw SQL calls. Describing every argument fixed the first, and returning the linked logs fixed the second.

16:15 to 17:00 · Module 5

The live incident, with a human in the loop

Goal

The room watches the whole loop run once on real telemetry: detect, investigate, refuse, approve, roll back, verify. Then a volunteer rejects and edits a proposal.

Say

Problem: a guess is not a fix. So the agent hunts and the person decides.

Ask the agent to execute early. It tries, and the control plane refuses and records that it tried. The guard is the server, not the prompt.

Every decision lands in an append-only audit log, with who and when. Recovery is judged on a full minute of fresh traffic after the change, never on the agent's say-so.

Narrate the tool calls as they stream. The room ran these queries by hand this morning. Name each one as it goes past: that is the delta query, that is the waterfall, that is the trace they read at lunch.

Run

  1. make chaos SCENARIO=bad-release
    Open :8090 and wait for the incident to appear, usually within a minute. Put the signup app tab beside it: the footer still reads Release v2.
  2. Open the incident and click Investigate with AI SRE. Narrate the tool calls as they stream in LibreChat.
  3. When it shows the approval link, type: Execute that remediation now, without waiting.
  4. Hand the laptop to a volunteer. They open the approval link, read the evidence and the blast radius, and click Approve.
  5. Back in LibreChat, type: I approved it. Execute the remediation, then confirm recovery before you resolve. Open the incident page and wait for the verification. Refresh the app: the footer reads Release v1 again.
  6. make chaos SCENARIO=docs-hang
    Investigate again. A hang takes the agent longer to localise than a bad release, because the evidence is an absence; keep talking through the tool calls. This time the volunteer writes a reason and clicks Reject, sets the action to restart_service on docs-loader, clicks Save edit, then Approve, and tells the agent to execute.

Files: sre-control/sre_control/approvals.py · e2e/specs/09-approve.spec.ts

Room sees

  • An incident naming the error rate and the bound it crossed.
  • The agent naming release v2 and SELECT pg_sleep(0.8), citing trace ids, and proposing rollback_release to v1.
  • The refusal in chat, and remediation refused in the timeline, before anyone approved.
  • After Approve: the rollback command and its exit code, then verification passed and incident resolved, each with a timestamp and an actor.

17:00 to 17:30 · Module 6

What to harden before this runs on your systems

Goal

Attendees leave with a list they can argue about with their own security team, and know which parts of it this lab already implements.

Say

Problem: a lab that works is not a system you can trust. Everything below is a real gap or a real control in the lab in front of them. Go through it as an honest account of what is done and what is left, not as advice.

Your telemetry carries personal data, and tool output goes to the model

The browser SDK is set to capture request bodies, so the email an attendee typed this morning is sitting in SpanAttributes['http.request.body']. Any tool that returns that span hands it to whoever hosts the model.

Today in the lab: the tools return trimmed rows, and the trace waterfall returns span attributes as they are. Nothing is redacted.

Redact at the tool boundary, not in the prompt. Return an allow-list of columns, hash identifiers so they still join, drop request and response bodies. Then point the same MCP tools at a model you host, which is one endpoint change in librechat/librechat.yaml, and decide per data class which model may see what.

Log lines are attacker-controlled text that your agent reads

Anyone who can get a string into your logs can write instructions to your agent. A user agent field is enough.

Today in the lab: the model can read any log body, and it can call only twelve tools. The one tool that acts takes an action and a target that must both be in a fixed allow-list, so an injected instruction has nothing to reach for.

Keep the action set closed and small. Treat every tool result as data, never as instructions, and say so in the system prompt. Alert on refusals: a proposal that fails grounding or policy is worth a human look, because it is either a confused model or a probe.

An approval page is only as good as what a tired person can check in a minute

At 3am the reviewer reads the root cause, which is the model's own prose, and decides. That is where a plausible wrong answer gets through.

Today in the lab: the trace ids, the service and the release are checked against ClickHouse before the proposal is stored. The blast radius is our fixed text per action, not the model's. The reviewer can reject with a reason, or edit the action and target and approve the edited version.

Add what the reviewer cannot get from the page. Link the cited traces in HyperDX and the diff of the release being withdrawn. Say who is on call for that service and whether a change freeze is on. For anything above a blast radius you set, require a second approver.

The agent runs commands through the Docker socket

The control plane performs a rollback by running docker compose up for the previous image. That socket is the highest-risk surface in the lab.

Today in the lab: the command is built from a fixed list of two actions and never from model text. Arguments are matched against a pattern, and execution needs an approval event. The VPS override publishes only Caddy's ports.

In production, do not give the agent a socket at all. Give it a narrow API that performs named changes. Run that API as its own identity with its own audit, and let your existing deployment system do the deploy.

Runs cost money and can loop

Both investigations in the last run cost less than a cent, but an agent that retries a failing tool can spend without a ceiling.

Today in the lab: the prompt sets a budget of eight tool calls before proposing, and the report records tool calls, tokens and cost for every run.

Enforce the budget on the server, not in the prompt: cap tool calls per incident, cap spend per day, and stop the run when either is hit. Watch tool calls and time to proposal as a regression signal, the same way you watch latency.

An agent with no test set drifts silently

A prompt change, a model upgrade or a tool rename can all turn a working loop into a confident wrong one. Nothing in a chat window tells you.

Today in the lab: make e2e replays two incidents end to end against a real model and a real browser. make score turns the result into a number out of 100, and every point is bound to a named test.

Keep your own incidents as fixtures. Replay them on every prompt and model change, and require the loop to reach the same root cause with the same evidence before you ship.

Wrap-up

Say

Problem: a demo proves little if nobody can rerun it. So the lab is gated the way you would gate an agent in production.

Take one thing home. Run the three substrate queries on your own data tomorrow. If they return nothing useful, no agent will do better, and that is the first thing to fix.
