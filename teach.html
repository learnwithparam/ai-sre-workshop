11:00 to 12:30 · Module 2

Anomaly detection inside the database

Goal

Attendees can write a 3 sigma bound in SQL and explain the two guards a production detector adds to it.

Say

The bound is the baseline mean plus three standard deviations, compared with the last minute. On a silent baseline the bound is zero, so a single failed request would page. The floor, min_delta of 5 points, stops that.

The detector adds two guards the query alone lacks. It drops baseline buckets that fall inside a past incident, so one outage cannot hide the next. And it keeps a fixed 10% SLO ceiling for the minutes when there is no clean baseline yet. Show both in the detector file.

The materialized view keeps per-minute rates up to date on every insert, so a dashboard reads a small table instead of scanning spans.

Run

docker exec -it clickstack clickhouse-client --param_baseline_minutes=10 --param_min_delta=0.05 --param_service=subscription-backend --param_minutes=60

Paste analyze_service_anomalies, then service_minute_rates.

15:00 to 16:15 · Module 4

Tools an agent can be trusted with

Goal

Attendees can explain why the lab gives the model semantic tools over workshop SQL, a read-only SQL escape hatch, and exactly one tool that can act.

Say

Raw text-to-SQL fails in predictable ways. In rehearsal the model guessed a column called service_name, and it searched for trace ids in spans that a hung request never exports. The semantic tools carry that knowledge, so the model does not have to rediscover it on every incident.

Two stories from building this lab, both worth telling. The first version of propose_remediation had a bare release argument, and the model filled it with the release to roll back to. And the trace waterfall used to answer "no spans" for a hung request, which sent the model into more than a dozen raw SQL calls. Describing every argument and returning correlated logs fixed both.

Every tool is classified in the policy file, and a structural test fails if one is not. Only execute_remediation can act. The ClickHouse user behind every agent query is read-only with a 10 second limit, so even raw SQL cannot write or starve ingest.

Run

docker exec sre-control python -m sre_control.probe no-token
docker exec sre-control python -m sre_control.probe write-attempt

16:15 to 17:00 · Module 5

The live incident, with a human in the loop

Goal

The room watches the whole loop run once on real telemetry: detect, investigate, refuse, approve, roll back, verify. Then a volunteer rejects and edits a proposal.

Say

The agent hunts; the human decides. The guardrail is the server, not the prompt: when we ask the agent to execute early, it tries, and the control plane refuses and records that it tried.

Every decision lands in an append-only audit log with who and when. Recovery is judged on a full minute of traffic after the change, never on the agent's say-so.

Run

  1. make chaos SCENARIO=bad-release
    Open :8090 and wait for the incident to appear, usually within a minute.
  2. Open the incident and click Investigate with AI SRE. Narrate the tool calls as they stream in LibreChat.
  3. When it shows the approval link, type: Execute that remediation now, without waiting.
  4. Hand the laptop to a volunteer. They open the approval link, read the evidence and the blast radius, and click Approve.
  5. Back in LibreChat, type: I approved it. Execute the remediation, then confirm recovery before you resolve. Open the incident page and wait for the verification.
  6. make chaos SCENARIO=docs-hang
    Investigate again. A hang takes the agent longer to localise than a bad release, because the evidence is an absence; keep talking through the tool calls. This time the volunteer writes a reason and clicks Reject, sets the action to restart_service on docs-loader, clicks Save edit, then Approve, and tells the agent to execute.
